01 · Summary

A benchmarking harness with an opinion.

VectorSuiteBench is a native macOS app for measuring the high‑performance limits of Apple‑Silicon vector math. The design philosophy is data‑dense and analytical — closer to a profiler than a consumer dashboard. Whitespace is earned, not assumed; every glyph supports the math it describes.

Platform
macOS 14+ · SwiftUI
Primary mode
Dark · System Tint
Charts

Design principles

P · 01
Trust the numbers, not the chrome.

Number cells are SF Mono with tabular figures; the UI is allowed to be utilitarian so a 12-row diff scans without re-flowing characters.

P · 02
One vibrant accent. One subject.

VectorCore owns the only saturated color in the app. Baselines (vDSP, Accelerate, Metal, naïve) are deliberately muted graphites so the reader's eye lands on the candidate under test.

P · 03
Refuse to mislead.

Failed verifications redact perf to — / ERR. Approximate math is visually demoted (hatched, dashed, muted) so a faster-but-wrong algorithm is never read as "winning".

P · 04
Statistical stance is visible.

P50 · P99 · P999 are first-class; no mean ever ships in a chart axis or table column. Mode (Single-Shot / Looped) is always labelled with a capsule on the same row as its number.

02 · Design system

Tokens

The token sheet ships as the first artboard in the design file. Surfaces are warm-neutral charcoals on a narrow lightness ramp (4 steps) so the eye can place rows without re-reading them. All accent colors share matched chroma (~0.16) and vary only by hue — they sit at the same perceived weight so badges don't shout over each other.

Typography

Two families, three roles. SF Pro Text (Inter as the web fallback) carries all UI labels, titles, and prose. SF Mono with monospacedDigit() / tabular-nums is strictly required for every number, every Git SHA, every axis label: a P99 number jittering by half a character across rows is the kind of cognitive tax that erodes trust in a benchmarking tool.

Badges, flags & treatments

The badge vocabulary is the most-reused atom across the app — every table row, chart header, and sidebar entry pulls from it. To keep them legible at small sizes they are always set in SF Mono, weight 700, with 0.4–0.6 tracking, in 3px-rounded chips.

✓ VERIFIED ✕ FAILED ! UNVERIFIABLE ⌇ BIMODAL SINGLE-SHOT LOOPED ⏱ TRUNCATED ~ APPROX STANDARD

Approximate-math treatment

Fast-math implementations get a stacked treatment, never just one signal:

  • Hatched fill in charts (45° lines, 5px pitch) — visually "lighter" than solid bars
  • Dashed 1px border on bars, points, and pill chips
  • Muted text color on the row's numbers (text-md not text-hi)
  • ~ APPROX pill in the implementation cell
DO
  • Place approximate points beside exact ones on the same axis — comparison visible, just demoted.
  • Show the error tolerance (e.g. ε ≤ 2⁻¹⁵) next to the badge.
DON'T
  • Hide approximate rows by default. Users need to see the cost/benefit at a glance.
  • Use color alone for "approximate" — color isn't enough at chart-point sizes.
03 · Information architecture

Three surfaces, one verb

The app does one thing: compare runs. Three surfaces support that verb:

Sidebar is the navigation primitive. Detail is the work surface — summary + content (table / charts / diff). The sheet is the only modal we use, and only for configuring a new run.

Comparisons happen by selecting two sidebar rows and entering Diff mode via the toolbar — the detail canvas swaps to a delta table with a hard-blocking error state if the two runs come from different hardware fingerprints (see edge cases).

04 · Main window

Run Dashboard

The main window is the app. It loads with the most recent run selected and the data table view active — chart-first feels analytical, but for the day-to-day "did my change regress something?" loop, the table is what eyes go to first.

Sidebar · Run History

Each row is three lines tall and renders the metadata a perf engineer actually scans for: time (relative grouping by day), preset as a colored chip, branch + short SHA in mono, and a duration · case count tail. A warn-colored dot in the row's top-right corner flags runs that experienced thermal throttling — the single most common reason to not trust a run.

DO
  • Group rows by relative date — "Today" / "Yesterday" / "May 13".
  • Surface SHA before commit message. Engineers triangulate by SHA, not subject.
DON'T
  • Show commit subject lines. They're long and rarely diagnostic.
  • Hide throttle/integrity flags behind a hover. They belong on the row.

Run Summary header

A 7-cell info-grid spanning the top of the detail pane. Each cell is one line of label (caption-style), one line of value (mono, tabular), and one line of context (mono, lo-color). Cell borders are 1px hair lines so the grid reads as one structure, not seven cards.

When the OS reports a thermal throttle during the run, the grid gets a warn-tinted banner above it explaining when and how many events occurred. This is non-dismissable; the signal is too important to be a tooltip.

Toolbar

Standard macOS chrome: + New Run (primary), ⇋ Compare, ↓ Export CSV, ⌖ Calibrate. The right side carries a small live-state chip: a green dot when idle, the machine model, and the core count — so an engineer kicking off runs over SSH can see at a glance whether the harness is busy.

05 · New Run modal

Configure benchmark run

A standard macOS sheet, dropped from the window's titlebar. The sheet is dense: five sections stacked vertically with a 180px label gutter on the left and the form controls on the right. That gutter gives every section a one-line title and a one-line hint without crowding the inputs.

Preset segmented control

Smoke · Standard · Full · Custom. Selecting a preset pre-fills every section below. Touching any control after that quietly flips the chip to Custom — no modal alert, just a visual cue that the preset has been mutated.

Multi-select inputs

Two patterns are used, each tuned to its content:

  • Operations is a 4-column grid of Checkbox chips. Each chip carries the operation name and its mathematical shorthand (dot · ∑ aᵢbᵢ). The math glyph is there so people don't have to remember whether "L2" means norm or distance.
  • Implementations is a 2-column grid of ImplChips. Each carries the impl's color swatch, library label, and an APPROX pill if it's a fast-math build. The additional density is justified because impls have richer metadata.

Both grids share the same selected-state treatment: 6% cyan fill, 0.5px cyan border, and the checkbox glyph fills with the accent. Unselected chips are 2% white with a hair-line border — quiet by default, so a half-configured run reads as half-configured.

Vector Sizes

A horizontally-wrapping pill grid at log-spaced powers of 2. Each pill is its own button: tap to toggle. This is the right pattern for a sweep with a fixed candidate set — engineers scan it as "16 to 16M, log-spaced, with 256k–4M turned off". A pair of slider handles would feel clinical but lose the per-size precision.

Budgets

A 3×2 grid of native-style select fields. Each has a one-line caption underneath in mono — for the wall-clock estimate, the caption is wired live to the footer so you can see the impact of every toggle. Captions also surface implications a perf engineer cares about: Warm-up — 20 iter · skip tells them the first 20 iterations don't count.

The live-estimate footer

Sticky to the bottom of the sheet. Three numbers in the accent color — ~342 cases, ~4m 50s, ~12 MB JSON — read first; a small breakdown grid on the right explains the math (5 ops × 2 dtypes · 5 impls · 7 sizes · shot + loop). The point is to make the cost of every checkbox click obvious in real time, so engineers don't accidentally kick off the 45-minute Full run when they meant Standard.

The Start button is the only emphasized primary in the entire sheet: 6% inner highlight + a 35% accent glow. ⌘↵ as a hotkey hint is the only mono text in the button.

06 · Chart suite

Five charts, one stance

Every chart in VectorSuiteBench shares the same architecture: a head strip with eyebrow / title / right-aligned pills (mode + flags), a plot region, and a foot strip with the key statistic readout. A sidebar legend sits inside the plot region rather than below it — at 1280px the layout already runs right-edge, so vertical real estate is the scarce resource.

The five charts mandated by the spec:

ChartAxesDistinguishing element
Throughput barsop · GFLOP/s or GB/sGrouped by impl. Hatched fills on approximate variants.
Latency histogramns (log) · countP50/P99/P999 rule-lines. Bimodal flag.
Percentile line chartvector size (log) · ns (log)Median + P99 lines scale together.
Roofline scatterFLOPS/byte (log) · GFLOP/s (log)Compute & bandwidth ceiling lines.
Memory pressurewall time · RSS (MB)Annotation bands at thermal events.

This document explores the two most technically risky: Roofline and Latency Histogram.

Roofline scatter

04 · ARTBOARD
Roofline · Compute vs Bandwidth ceiling
820 × 560 · section charts · id roofline
↗

The roofline plot is the most information-dense chart in the suite. It is also the one where "approximate math hatches" and "bimodal warnings" are most likely to make the picture unreadable. The approach:

  • Ceilings are the chart's primary structure. The two rooflines (peak compute, peak bandwidth) are 2.2px solid in --vc — they earn the only saturated stroke in the plot. A 4% accent fill below them creates a subtle "feasible region" floor.
  • Solid points = exact math. Dashed-stroke open rings with a slash = approximate. The ring + slash is more legible at scatter sizes than a hatched fill.
  • Annotation boxes anchor the lesson. One target callout ("VectorCore axpy ƒ16 · 400 GFLOP/s · 98% peak") tells the engineer what to take away — the chart is not just a plot, it argues a point.
  • Balance line. A faint dashed vertical at AI ≈ 10 marks where kernels stop being memory-bound. Without this the diagonal looks decorative.

Latency histogram

04 · ARTBOARD
Latency Histogram · Bimodal
820 × 560 · section charts · id histogram
↗

The histogram makes the most of its color budget by varying treatment, not hue:

  • Bins are all the same cyan. The right-tail bins (past P99) get a warn fill so the tail itself is visible without an annotation pointing at it.
  • Hatched bars in the second mode. When the scheduler migrated to an E-core mid-run, the second hump renders as hatched bars rather than a different color. The reader sees "two modes" and the hatch tells them "this is the migration".
  • Top brackets. Square brackets at the chart's top label each mode with a hit count. This is a quieter, more accurate replacement for chart-area annotation lines.
  • Three dashed rule-lines for P50 / P99 / P999 in text-hi / warn / fail, with anchored mini-tags in the upper-right of the plot. The tag chip's stroke matches the line color so they're locked together visually.
  • The BIMODAL pill drives an inline explainer. The legend includes a short prose note that names the root cause ("scheduler migrated to E-core, 60/200") and suggests the fix ("pin to P-cores"). Charts that diagnose are more useful than charts that describe.
  • Mode pill in the header (SINGLE-SHOT) is required — the same data in LOOPED mode would have a wildly different distribution and reader needs to know which it is before reading anything else.
07 · Edge cases

States we have to get right

Cross-hardware diff (blocked)

Diffing an M1 run against an M3 run is meaningless. The Diff pane refuses with a full-bleed blocking state and explicit copy: "Cross-hardware comparisons are disabled to prevent misleading data." A secondary affordance offers to filter the sidebar to runs on the matching fingerprint.

Empty state · first launch

Before any chart can render meaningfully, we need to know what the user's machine is actually capable of. The main canvas shows a centered cpu.mac hero icon, "Hardware Calibration Required", and a primary Measure Peaks (~30s) button. While running, a terminal-style status feed (mono, text-md) renders below a small circular spinner.

Failed verification

Every perf cell in the row redacts to —; GFLOP/s and GB/s become ERR in --fail. The row's Operation cell remains in text-hi so the row is still findable in a scan. Status shows the reason (ulp>1024, nan, etc.).

Thermal throttle during run

Warning banner above the Run Summary header (covered above). The Cases summary cell tightens to 342/342 · 0 failed · 4 ⚠. Throttled cases stay in the table but their rows get a faint amber-tinted background.

Run still in progress

The selected row in the sidebar shows a small spinning dot in the throttle slot. The detail pane renders rows as they stream in, with an ⋯ trailing pill in the implementation cell of the in-flight case. Cancel lives in the toolbar.

08 · Open questions

For your review

  1. Sidebar density. The current row is three lines, ~62px tall. With heavy users running 50+ benchmarks/day, do we want a "compact" toggle that drops to a one-line variant (time + SHA + status)?
  2. Mode pill location. Right now SHOT / LOOP lives inside the Mode column of the table. Alternative: make Mode a filter at the top and never repeat it in rows — would simplify cells but lose at-a-glance scannability when mixed-mode tables are exported.
  3. Approximate-math placement. Should fast-math rows sit interleaved with their exact counterpart (current) or grouped at the bottom of each operation block?
  4. Diff visual. Side-by-side or merged delta table? The delta-table prototype reads tighter but it's harder to spot a column where target is missing a verification baseline has.
  5. Hardware fingerprint detail. Currently a single string ("M3 Max · 14C / 30G"). Worth expanding to a popover with full chip details (cluster sizes, base/boost clocks, memory channels)?
  6. Color-blind paths. The current diff coloring relies on hue. Should we layer icons on the delta column (▼ / ▲) or only on opt-in?
